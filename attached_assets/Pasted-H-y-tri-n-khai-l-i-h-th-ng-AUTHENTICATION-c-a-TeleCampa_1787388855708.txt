========================
1. MỤC TIÊU
========================

Xây dựng hệ thống tài khoản cho TeleCampaign với 2 chức năng:

- Đăng ký tài khoản
- Đăng nhập tài khoản

Người dùng đăng ký bằng:

- Tên đăng nhập (username)
- Mật khẩu
- Xác nhận mật khẩu

SAU ĐÓ dùng:

- Username
- Password

để đăng nhập.

TUYỆT ĐỐI KHÔNG sử dụng Google Login.

Không sử dụng Google OAuth.

Không bắt buộc email.

Không yêu cầu OTP email.

Không yêu cầu số điện thoại.

Không tạo tài khoản thông qua Google.

========================
2. QUAN TRỌNG: KIỂM TRA AUTH HIỆN TẠI
========================

Trước khi sửa code, hãy kiểm tra toàn bộ project để xác định authentication hiện tại đang sử dụng gì.

Kiểm tra:

- frontend authentication
- backend authentication
- database schema
- user table/model
- session/cookie
- middleware auth
- protected routes
- API authentication
- Clerk hoặc các thư viện authentication hiện tại nếu đang tồn tại

KHÔNG được tạo thêm một hệ thống authentication độc lập nếu project đã có authentication hiện tại.

Nếu project hiện đang dùng Clerk nhưng yêu cầu Username + Password không phù hợp với cấu hình hiện tại, hãy kiểm tra khả năng dùng Password Authentication đúng cách.

Nếu kiến trúc hiện tại không phù hợp với username/password native, hãy chọn phương án an toàn và tương thích nhất với database/backend hiện tại.

Mục tiêu là chỉ có MỘT hệ thống authentication duy nhất.

Không để xảy ra tình trạng:

- Clerk quản lý một user
- Database tự quản lý một user khác
- Hai hệ thống session khác nhau
- User bị tạo duplicate

========================
5. USERNAME
========================

Username phải là định danh duy nhất.

Khi đăng ký:

- trim khoảng trắng đầu/cuối
- không cho username rỗng
- không cho username trùng
- username không phân biệt hoa thường khi kiểm tra trùng

Ví dụ:

Admin
admin
ADMIN

phải được coi là cùng một username nếu hệ thống không có yêu cầu đặc biệt khác.

Nên chuẩn hóa username trước khi lưu.

Cho phép username dễ sử dụng, ví dụ:

teleuser123
nguyenvana
shoptele

Không cho phép username chứa ký tự nguy hiểm hoặc gây lỗi routing/database.

Có validation rõ ràng.

========================
6. PASSWORD
========================

Không bao giờ lưu password dạng plaintext.

Password phải được hash bằng thư viện/thuật toán an toàn phù hợp với stack hiện tại.

Không tự viết thuật toán hash.

Không log password ra console.

Không trả password trong API response.

Không lưu password trong localStorage.

Không lưu password trong frontend state lâu hơn mức cần thiết.

Khi đăng nhập phải verify password với password hash.

========================
7. ĐĂNG KÝ
========================

Flow:

User mở /register.

User nhập:

username
password
confirm password

Frontend validation trước.

Sau đó gửi request tới backend.

Backend phải kiểm tra lại toàn bộ validation.

Backend kiểm tra username đã tồn tại chưa.

Nếu đã tồn tại:

Hiển thị:

"Tên đăng nhập đã tồn tại"

Nếu password và confirm password khác nhau:

"Mật khẩu xác nhận không khớp"

Nếu dữ liệu không hợp lệ:

Hiển thị lỗi rõ ràng.

Nếu hợp lệ:

1. Hash password.
2. Tạo user trong database.
3. Tạo session đăng nhập.
4. Trả kết quả thành công.
5. Redirect vào dashboard.

Không được tạo duplicate user nếu request đăng ký được gửi nhiều lần.

Database phải có unique constraint cho username.

Không chỉ dựa vào frontend để chống username trùng.

========================
8. ĐĂNG NHẬP
========================

Flow:

User nhập:

username
password

Backend:

1. Tìm user theo username đã chuẩn hóa.
2. Nếu không tồn tại → thông báo thông tin đăng nhập không đúng.
3. Verify password.
4. Nếu password sai → thông báo thông tin đăng nhập không đúng.
5. Nếu đúng → tạo session.
6. Set cookie/session an toàn.
7. Redirect về dashboard.

Không trả về thông tin nhạy cảm.

Không tiết lộ quá chi tiết rằng username có tồn tại hay không trong trường hợp không cần thiết.

========================
9. SESSION
========================

Session phải được quản lý an toàn theo kiến trúc backend hiện tại.

Nếu sử dụng cookie:

- HttpOnly
- Secure khi chạy production
- SameSite phù hợp
- có expiration
- không lưu session token trong localStorage nếu không cần thiết

Logout phải:

- xóa/invalidate session
- xóa cookie liên quan
- đưa user về trang đăng nhập

Không để user đã logout tiếp tục truy cập dashboard bằng session cũ.

========================
11. USER DATA ISOLATION
========================

Đây là phần cực kỳ quan trọng.

Mỗi user chỉ được nhìn thấy và thao tác dữ liệu thuộc về chính user đó.

Ví dụ:

User A đăng nhập:

→ chỉ thấy Telegram accounts của A.
→ chỉ thấy campaigns của A.
→ chỉ thấy destinations của A.
→ chỉ thấy scheduled posts của A.
→ chỉ thấy activity logs của A.

User B:

→ không được đọc/sửa/xóa dữ liệu của A chỉ bằng cách thay đổi ID trên request.

Tất cả API phải kiểm tra ownership ở backend.

Không tin userId do frontend gửi lên.

User ID phải được lấy từ session/authenticated user.

========================
12. DATABASE
========================

Kiểm tra schema hiện tại trước khi thay đổi.

Nếu đã có bảng users thì tận dụng bảng hiện tại.

Nếu cần migration:

- tạo migration rõ ràng
- không xóa dữ liệu hiện tại
- không reset database production
- không làm mất user hiện có

User tối thiểu cần có:

- id
- username
- passwordHash
- createdAt
- updatedAt

Nếu schema hiện tại có các field khác cần thiết thì giữ nguyên.

Username phải UNIQUE.

Nếu user hiện tại được tạo bằng authentication cũ, không tự ý xóa.

Phải đảm bảo migration an toàn.

========================
18. BẢO MẬT
========================

Trước khi hoàn thành phải kiểm tra:

- SQL injection
- authentication bypass
- IDOR
- session fixation
- insecure cookie
- password plaintext
- password logging
- thiếu authorization ở API
- user A đọc dữ liệu user B
- user A sửa dữ liệu user B
- user A xóa dữ liệu user B
- duplicate username
- brute-force protection/rate limit phù hợp

Không đưa secret vào frontend.

Không commit secret.

Không hardcode API key.

Không hardcode database password.

Không hardcode session secret.

========================
19. NẾU ĐANG DÙNG CLERK
========================

Nếu project hiện tại đang sử dụng Clerk:

Không tự ý xóa Clerk ngay.

Trước tiên kiểm tra:

- package @clerk
- ClerkProvider
- SignIn
- SignUp
- middleware
- currentUser
- auth()
- session
- user mapping trong database

Sau đó xác định cách triển khai username/password tương thích.

Nếu Clerk hiện tại không phù hợp với yêu cầu username/password mà không có email/Google, hãy đánh giá kiến trúc trước khi thay đổi.

Nếu cần thay authentication provider thì phải:

- migration user an toàn
- giữ dữ liệu user
- giữ ownership
- giữ protected routes
- giữ session security

Tuyệt đối không để tồn tại hai hệ thống auth song song.

========================

Không dùng mock authentication.

Hãy đọc toàn bộ code hiện tại trước khi chỉnh sửa để tránh phá các chức năng Telegram Campaign, queue, worker, campaign, destination, calendar và activity log đang có.

Nếu phát hiện vấn đề kiến trúc lớn có thể làm mất dữ liệu hoặc phá authentication hiện tại, hãy dừng trước bước destructive change và báo rõ vấn đề thay vì tự ý xóa/sửa dữ liệu.

Sau khi hoàn thành, hãy báo cáo ngắn gọn:

1. Đã sửa những file nào.
2. Authentication hiện tại đang hoạt động theo kiến trúc nào.
3. Database đã thay đổi gì.
4. Đăng ký username/password hoạt động ra sao.
5. Đăng nhập hoạt động ra sao.
6. Session được bảo vệ thế nào.
7. Đã test những flow nào.
8. Typecheck/build có PASS hay không.
9. Có vấn đề nào còn cần tôi xử lý hay không.

USER
